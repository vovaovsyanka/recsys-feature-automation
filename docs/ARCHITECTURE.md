# Архитектура

## Поток данных

```
сырые файлы (data/raw)
   │  scripts/00_prepare_data.py
   ▼
таблица событий (data/processed/*_events.parquet)       единая схема: uid, item_id, ts, et, org, ratio, tlen, artist, album
   │  scripts/04_build_rows.py, 30_kion_rows.py
   ▼
строки (якорь, пользователь, кандидат) + метки (data/rows/<tag>)     фиксируются один раз для всех моделей
   │  FeatureStore.ensure()
   ▼
кэш признаков по якорям (data/fstore/<tag>)             считается лениво, пакетами, сохраняется
   │  T.build_mat()
   ▼
матрица признаков → LightGBM / оценка метриками
```

Все модели сравниваются на одних и тех же строках: это условие честного сравнения (одинаковые кандидаты и доступная информация).

## Пакет `src/recsys`

| модуль | назначение |
|---|---|
| `config.py` | пути, число потоков, имена наборов строк |
| `protocol.py` | якоря, окна меток, проверка отсутствия пересечения меток обучения с val и test |
| `tracking.py` | оформление эксперимента: конфиг, лог, результаты, время по стадиям, версия кода |
| `data/` | сборка единой таблицы событий для Yambda и KION |
| `candidates/` | генерация кандидатов и меток (источники кандидатов, группы пользователей) |
| `features/spec.py` | грамматика признаков: `ключ.канал.агрегат.окно` и производные `d:ratio`, `d:diff`, `d:urank` |
| `features/engine.py` | вычисление признаков по посуточным таблицам; читает только данные до момента прогноза |
| `features/store.py` | кэш признаков по якорям, внешние признаки, подвыборка пользователей |
| `features/grammar.py` | пул признаков, из которого выбирают автоматические методы |
| `features/manual_*.py` | ручные наборы признаков (Yambda и KION) |
| `features/sets.py` | реестр наборов, доходящих до финального сравнения |
| `models/gbdt.py` | сборка матриц и обучение LightGBM |
| `models/sequence.py` | модель над историей: внимание, зависящее от кандидата, с обучаемыми временными ядрами |
| `models/embeddings.py` | ALS и LightGCN на контрольных точках |
| `search/sandbox.py` | песочница для честного сравнения методов поиска признаков |
| `search/methods.py` | случайный выбор, отбор из пула, OpenFE, обучаемые окна |
| `search/llm_agent.py`, `llm_client.py` | поиск признаков языковой моделью и клиент (Ollama Cloud, запасной локальный сервер) |
| `evaluation/metrics.py` | NDCG, Recall, AUC, LogLoss по группам и бутстреп по пользователям |

## Как устроена защита от утечек

1. **Признак читает только прошлое по построению.** `Engine` берёт из посуточных таблиц строки с `day < a` и события с `ts < a`.
   Новый признак нельзя «написать неправильно»: он обязан быть строкой грамматики. Это относится и к признакам,
   предложенным языковой моделью: код модели никогда не исполняется.
2. **Тест на возмущение будущего** (`scripts/05_leakage_tests.py`). События после момента прогноза заменяются случайными,
   признаки пересчитываются и должны совпасть побитово. Чувствительность теста подтверждает «канарейка»: окно, захватывающее
   сутки якоря, обязано расходиться.
3. **Метки изолированы по времени.** `protocol.check_protocol` проверяет, что окна меток обучающих якорей заканчиваются
   до первого якоря val, а окна val — до первого якоря test.
4. **Векторные модели** (ALS, LightGCN) обучаются на контрольных точках только на данных до точки; словари строятся по данным до val.
5. **Test.** Все скрипты поиска и подбора работают на train и val. Обращения к test журналируются.

## Как добавить свой признак или метод

* Признак: добавить строку грамматики в `features/manual_yambda.py` (ручной набор) — или он появится автоматически в пуле,
  если укладывается в `features/spec.py`. Новый тип агрегата — ветка в `Engine._daily_aggregates` и правило допустимости в `Spec.valid`.
* Метод поиска: функция в `search/methods.py`, которая получает песочницу `Proxy`, базовый набор и пул, а возвращает список
  признаков; оценка — только через `Proxy.evaluate`, чтобы условия сравнения совпадали.
