## 2. Задача (Yambda, основная)

**Ранжирование «следующих суток»:** в момент-якорь `a` (00:00 суток) для пользователя `u` ранжируем кандидатов `i`.
Положительные: треки, прослушанные пользователем с долей ≥ 50% (Listen+) в окне `[a + 30 мин, a + 30 мин + 24 ч)`.
- 30-минутная пауза - как в Global Temporal Split Yambda (V2: полный текст статьи): имитирует задержку обновления модели.
- Фичи используют только события с `timestamp < a`. Повторы разрешены (как в протоколе статьи, по тексту не исключаются).
- В выборку попадают (якорь, пользователь) c ≥ 1 положительным и непустой историей до `a` - это условная оценка, как в статье
  (там пользователи с пустой историей отбрасываются; про отбор по наличию позитивов в окне в статье явного указания нет -
  **расхождение фиксируем, сравнение с таблицей статьи только ориентировочное**).

### Разбиение по времени (глобальное)
| Часть | Якоря (сутки с начала) | Использование |
|---|---|---|
| train | 150…283 (до 134 якорей; по умолчанию подвыборка с шагом, см. эксперименты) | обучение моделей |
| val | 285…291 (7 суток) | выбор признаков, гиперпараметров, архитектур |
| test | 293…299 (7 суток) | **только финальная оценка**, каждая финальная модель - один раз |
| не используется | сутки 284, 292 (буферы), сутки 300 (неполные, 0.93 суток) | - |

Ограничение (проверяется assert-ом в `src/recsys/protocol.py::check_protocol`): метки любой обучающей строки должны быть известны
к моменту первого якоря val: `a_train + 30 мин + 24 ч ≤ a_val_min`, аналогично val→test. Из-за 30-минутной паузы
последний обучающий якорь = сутки 283 (при якоре 284 метки заканчивались бы на 1800 с позже начала val), последний якорь val = 291.

Нарушения, которые мы специально **предотвращаем**: (1) события из окна метки в признаках; (2) метки val/test в обучении;
(3) отбор признаков/гиперпараметров по test; (4) статистики (target encoding, ALS, популярность), посчитанные на данных после якоря.

## 3. Кандидаты (одинаковы для всех сравниваемых моделей)
Объединение источников, считаемых по истории `< a`: (S1) топ по затухающему счётчику пользователя, (S2) топ по полному счётчику,
(S3) популярное у артистов пользователя, (S4) глобально популярное за 7 суток. Размеры источников подбираются в E03
по Recall кандидатов на **train/val** (не на test) при бюджете ≈200 кандидатов на пару. Верхняя граница метрик = recall кандидатов,
всегда публикуется рядом с результатами. Позитивы вне кандидатов считаются промахами (знаменатели NDCG/Recall - по всем позитивам).

## 4. Метрики
Основные (на группу «якорь×пользователь», затем среднее по группам): NDCG@10, NDCG@100, Recall@10, Recall@100.
Pointwise: LogLoss, ROC-AUC (по всем строкам кандидатов). Доверительные интервалы - парный бутстреп по пользователям (1 000 повторов);
разницы моделей даются с ДИ. Для ключевых моделей - 3 сида.
Почему не sampled-метрики: Krichene & Rendle (KDD 2020, `SOURCES.md` F3) показали несогласованность.

## 5. Модели и эксперименты

**Базовый уровень (сильный базлайн, критерий 1):**
- B0: Random, MostPop, DecayPop, «затухающий счётчик пользователя»; ItemKNN как справочный (на кандидатах).
- B1: LightGBM (lambdarank и binary) на вручную спроектированных признаках: user / item / user×item (прямые) / user×artist, user×album (косвенные).
  Ручные окна фиксированы заранее: 1, 7, 30 суток и всё время (как сделал бы практик), без подгонки под val.
- B1+: тот же набор, гиперпараметры подобраны Optuna на val (бюджет фиксирован).

**Автоматизация признаков (критерий 2, идея 1):** общая грамматика `FeatureSpec = (ключ, фильтр событий, агрегат, окно)`;
любой признак компилируется в один и тот же движок и проходит **автоматический тест на утечку** (возмущение будущего не меняет признак).
Методы поиска (равные бюджеты по числу обучений и по времени):
- A1 Random-grammar (контроль);
- A2 DFS-генерация всех + отбор по важности (Kanter & Veeramachaneni; OpenFE-стиль отсечки);
- A3 OpenFE-style «feature boosting» (прирост на val при warm-start от базовой модели), coarse-to-fine;
- A4 Обучаемые окна: затухающие счётчики с полуperiodом, найденным оптимизацией на val (вопрос «почему 7 суток?»);
- A5 LLM-агент (CAAFE/LLM-FE-стиль): предлагает спецификации грамматики по раундам с обратной связью val-прироста.
  Агент - открытая модель gpt-oss:120b через Ollama Cloud (ключи в переменных окружения, запасной вариант - локальный LM Studio); все промпты и ответы сохраняются в JSON.

**Альтернативные модели (критерий 2, идеи 2 и 3):**
- C1 target-aware attention над историей (DIN/ETA-стиль, `SOURCES.md` C1, C4) на тех же строках (якорь, пользователь, кандидат);
- C2 SASRec-подобная модель (retrieval по полному каталогу) для сверки с Table 6 статьи;
- C3 граф user–track–artist (LightGCN-стиль), точечно-временные эмбеддинги;
- C4 гибрид: GBDT + скоры C1/C3 как признаки (стекинг строго «вне времени»).

**Анализ (критерий 4):** аблация групп признаков; важность; кривые «качество vs число признаков/время»;
масштабирование по числу пользователей (1k/3k/10k) и по длине истории; затраты (время, RAM, GPU);
отдельные срезы: повтор vs новое, рекомендательное vs органика, лёгкие vs тяжёлые пользователи.

**Второй домен (KION):** тот же протокол «следующая неделя» на дневной гранулярности; кандидаты - топ по популярности и жанровому сродству.

## 6. Защита от утечек (обязательные тесты, `scripts/05_leakage_tests.py`)
1. **Возмущение будущего:** все события с `ts ≥ a` заменяются случайными - признаки пар (u, i) должны совпасть побитово.
2. **Канарейка:** намеренно протекающий признак должен быть пойман тем же тестом (проверка чувствительности теста).
3. **Контроль меток:** перемешанные метки внутри групп ⇒ NDCG ≈ случайный; AUC ≈ 0.5.
4. **Проверка разбиения:** assert на непересечение окон меток и якорей train/val/test.
5. Каждый сгенерированный (в т.ч. LLM-агентом) признак проходит тест 1 до обучения.

## 7. Учёт ресурсов
Каждый эксперимент (`src/recsys/tracking.py`) пишет: wall-time по стадиям, CPU-время, пик RAM, GPU-память для torch, версию кода (хэш), хэши данных.
Аппаратная платформа: Intel i5-11400H (6 ядер / 12 потоков), 64 ГБ RAM, RTX 3050 Laptop 4 ГБ.

## 8. Угрозы валидности (заранее)
- Данные - 1%-выборка пользователей; результат на 10 тыс. пользователей может не переноситься на 1 млн (проверяем кривой масштабирования).
- Рекомендательные прослушивания зависят от прежней системы Яндекс.Музыки (ликвидность/смещение): модель частично учит политику показа; поэтому срезы organic/recommended.
- Один временной интервал (301 сутки), сезонность не охвачена.
- Подбор окна и признаков по val с последующей оценкой на 7 test-сутках: риск переобучения на val снижаем фиксированным бюджетом поиска и сравнением с контролем A1.
- LLM-агент в эксперименте - внешняя модель; воспроизводимость ограничена версией модели (фиксируется в логе).
